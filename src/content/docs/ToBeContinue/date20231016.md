## Git

git 是一个分布式版本管理系统，他的存储区域有如下

1. 远程仓库
2. 本都仓库（每个人都有自己的本地仓库）

本地存储可以细分如下

1. 工作目录
2. 索引区域（暂存区）
3. 本地仓库

### git objects

可通过 `git cat-file` 去查看每个文件存储的内容

1. git blob object ：存储文件的具体信息，以文件内容为 HASH 名称
2. git tree object：存储一次快照，其包含文件结构（文件夹，文件名，权限等等），每个文件对应的 object blob
3. git commit object：存储一次提交，包含此次提交的信息，对应的 tree object，parent commit object

### git refs

1. git heads ref：记录了每个分支对应的 commit
2. git tags ref：记录了每个 tag 对应的 commit

### git index

git index 文件记录了暂存区每个文件对应的 object blob

### 一次提交

1.  在 master 分支 执行 git checkout dev
    创建一个新的分支，在 .git/refs/heads 中创建一个新的文件 dev，dev 中记录了当前分支的 HEAD，也就是 commit object，且此时 dev HEAD === master HEAD
2.  新建一个 code.txt，文件内容为 1+1=2，执行 git add code.txt
    在 .git/objects 中创建一个 blob object 用于存储当 code.txt 文件内容，并在.git/index 中建立一个索引，即 code.txt => git blob object
3.  执行 git commit
4.  在 .git/objects 中创建一个 tree object，其中保存了当前的目录信息及其对用的 blob，如下所示

```
100644 blob $BlobObject base.ts
```

2.  在 .git/objects 中创建一个 commit object，记录其 commit 信息， tree object，parent commit object，如下所示

```
tree $TreeObject
parent $ParentCommitObject
author $author
committer $committer

$commit message
```

3.  更新 .git/refs/heads/dev 中的 HEAD，指向新的 commit object

### 一次合并

在 master 分支集中`git merge | rebase dev`，即此时 mines 是 master 分支，others 为 dev 分支

git 的合并是基于每个文件逐行去合并，当同一行被两个人修改 git 会如何处理呢

双方合并

mines 在 10 行代码是 `const a = 1`
others 在 10 行的代码是 `const a = 2`

此时如果只是双方合并的话，git 无法得知到底需要保存谁的结果

三方合并（Tree-Way Merge）

找到一个比较基准即 base，假设 base 的 10 行代码为 `const a = 1`，此时我们可以知道 mine 对于 base 来说是没有变化的，而 others 对于 base 来说是有变化的，因此会采用 others 的代码，git 选取 mine 合 others 的公共祖先节点（commit）为 base。

那么冲突是怎么来的呢？是 mine 和 others 对于 base 来说都有修改，例如 base 的代码是 `const a = 3`，此时 git 就不知道该采用谁的代码了，需要人为来解冲突

当进行合并的时候，不会像 dev 合并到 master 这么简单，分支之间交错，错综纷杂，有可能在 mine 和 others 之间能找到多个公共祖先，这个时候以不同的祖先为 base 可能得到的不同结果，所以 git 采取**递归三方合并**，在存在多个公共祖先的时候，git 会去对该公共祖先进行一次合并，找到公共祖先的公共祖先，以其为 base，把公共祖先合并了，再以合并后的为 虚拟的 base 来合并 mine 和 others。需要注意的是公共祖先的公共祖先的合并不会体现在 commit 中，此次是虚拟的

#### git merge

git merge 有几种不同的模式，git 会智能的选取某个模式，当然也可以直接指定 `git merge -s $策略`，常见的如下

1.  Fast forward：在合并时，mine 不存在任何修改，合并 others 时，mines HEAD 会直接指向 other HEAD。该模式无法通过 `-s` 来执行，算是一种特殊的合并模式
2.  Recursive（递归合并）：最常用的合并模式，按照三方合并，并创建一个新的 commit，mine HEAD 指向该 commit。此时新的 commit 会有点特殊，该 commit 会同时指向两个父 commit

```
ree 4cc7497ed7b0722aac0e485d90353e45f7a40050
parent 73e48c286e63f24dc77205851fdeee9740e19707
parent 564027a5a9caa0299b868a5352d3559e8ca29b3e
author keven <yuezmkeven@gmail.com> 1695310479 +0800
committer keven <yuezmkeven@gmail.com> 1695310479 +0800
```

3.  Ours（保留自身）：保留 mine，忽略掉 others，但是会有一个合并记录。适用于舍弃掉代码但又想保存一个记录
4.  ...

#### git rebase

git rebase 时，先找到公共祖先，然后把 mine 的每一个 commit 去续接（平移）在 other 之后，由于父级的 commit 出现变更，则 git rebase 会**创建新的 commit** 来记录这些提交。可以想象成把 mine 的 commit 依次取 others 中**重演一次**

#### 最近公共祖先

如何寻找两个分支或者说两个 commit 的最近祖先。每个分支指向的是一个 commit，每一个 commit 又有一个指针指向父 commit（多个父级），即只针对某一个分支来说，他是一个树形数据结构，对于整个 git 项目来说，他是一个无环有向图

针对两个分支来说，可以有如下方式求得最近公共祖先

1. 标记，以 HASH 存储已经遍历过的节点
   1. DFS: 对某一个分支遍历一次，以 HASH 表存储所遍历的 commit，再遍历另一个分支
   2. BFS: 可以想象为两个波纹在扩散，当存在交点时（当前遍历的这个 commit 在另一个树里面已经遍历了）
